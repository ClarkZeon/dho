# 카탈로그 목록 조회 기준 (1000개)

관리자·유저 사이트 도감/리스트 API의 **전량 조회 vs 서버 페이징** 기준입니다.  
에이전트·개발 시 이 문서를 따르고, 같은 질문을 반복하지 않습니다.

## 규칙

| 등록 건수 | 조회 방식 | UI |
|-----------|-----------|-----|
| **1000개 이하** | `GET` 전량 조회 (`list*`) | 클라이언트 검색·정렬·(필요 시) 페이지 UI만 |
| **1000개 초과** | 서버 페이징 (`q` / `limit` / `offset` / `sort` / `dir`) | 검색·정렬 변경 시 refetch |

- 임계값: **1000** (초과 시에만 서버 페이징 필수).
- 건수는 `catalog_stats` / 관리자 대시보드 카운트를 참고. 크게 늘면 이 표를 갱신한다.

## 카탈로그별 현황

| 카탈로그 | 대략 건수 | 방식 | 비고 |
|----------|-----------|------|------|
| 선박 | ~741 | 전량 | 가속도·비교도 전량 필요 |
| 항구(도시) | 1000 이하 | 전량 | |
| 필드 | ~563 | 전량 | 연결된 장소(2차 필드) 포함 |
| 퀘스트 | 1000 초과 | **서버 페이징** | `listQuestsPage`, 페이지당 15 |
| 발견물 | (미정·보통 1000 이하 가정) | 전량 유지 후 초과 시 전환 | |
| 스킬 (분류: 언어 등) | 소수 | 전량 + 클라이언트 페이징 UI | |
| 선박 재료 | 소수 | 전량 + 클라이언트 페이징 UI | |
| 소비품 | (증가 중) | 전량 유지, **1000 넘으면 서버 페이징** | |

## 구현 시 체크

1. 새 카탈로그를 추가할 때 예상 건수를 이 표에 적는다.
2. 1000 초과가 확정되면 API·`api.ts`·관리자/유저 리스트를 퀘스트와 같은 패턴으로 맞춘다.
3. 전량 조회여도 테이블에 **페이지 UI(15개 등)** 를 둘 수는 있다. 그건 UX용이며, 데이터는 이미 클라이언트에 있다.
4. **선박**은 비교·가속도 때문에 전량 유지를 우선한다 (1000 넘어도 먼저 제품 필요).

## 관련 코드

- 퀘스트 페이징: `server/questStore.mjs` → `listQuestsPage`, `GET /api/quests?q&limit&offset&sort&dir`
- 통계 캐시: `server/adminStats.mjs`, `sql/017_catalog_stats.sql`
